# AGENTS.md

Working brief for an AI coding agent, not documentation for people (the README covers that): the rules, invariants and gotchas needed to change this project correctly without rediscovering them.

## Hard rules
- **whypkg never syncs or modifies the system.** It only reads package state; a write would betray the whole premise ("just tell me why this is here").

## Invariants and gotchas
- Adding a distro is one new `src/backend/<name>.rs` (implement the `Backend` trait) plus one line in `detect()`; nothing else changes. rpm distros share `dnf::RpmDump` (the four `rpm -qa` dumps and the capability graph), so `zypper.rs` only adds the manual set (`i+` in `zypper search --installed-only`), orphans (`zypper packages --orphaned`, never the `(System Packages)` column, which only means no repo holds that exact version) and upgrades. zypper cannot tell a local rpm from an orphan, since its history log is root-only, so it never yields `Origin::Local`. `detect()` checks every front end (apt, pacman, dnf, zypper) before the bare `rpm` they share, because distros package each other's managers. Parsing in each backend is pure functions; they are tested against captured real output in `tests/fixtures/` via `include_str!`, zypper's tables and `apt-get -s autoremove` included.
- Flatpak, cargo, pipx, uv and npm are NOT `detect()` backends: they *coexist* with the system package manager, so each reads into a `backend::Layer` (`flatpak.rs`, `cargo.rs`, `venv.rs` for pipx and uv, `npm.rs`) that `load::read_world` merges onto whatever `World` the system backend built, each package tagged with its `Source`. `read_world` runs the system backend and every layer reader on threads of their own at once, so the layers cost nothing on top of the half second the package manager takes; with no system backend it starts from `World::empty()`. The sources a run reads come from `--only` (browser, `why`, `leaves`) or else `Sources::all_but(config.skip)`; `pending` reads only `Source::System`, since nothing else reports upgrades.
- The layers never run their installer: cargo is read from `~/.cargo/.crates2.json` (description and `[package.metadata] runs` from the `Cargo.toml` of the source copy cargo keeps under `registry/src`, or of the folder of a `--path` install; a `--git` install keeps none), pipx and uv from each tool's virtualenv (`pipx_metadata.json` or `uv-receipt.toml` names the tool, every `.dist-info` is a package, `Requires-Dist` the edges, `REQUESTED` marks what the user asked for, `RECORD` the size), npm from the global `node_modules` folders (`NPM_CONFIG_PREFIX`, `~/.npmrc`'s `prefix=`, node's own prefix, `/usr/local`) and every `package.json` under each global, resolved the way node resolves (nearest `node_modules` up the tree). npm and corepack in node's own global folder (`<node's prefix>/lib/node_modules`, never a folder merely under the prefix such as `/usr/local`) are skipped as bundled, a pipx tool in both the new and the old pipx home is read from the new one, and a global under `/usr` (not `/usr/local`) that the system package manager owns (`Backend::owners`) is a system package (Arch's `typescript`), never listed twice; that is why `read_world` detects the backend even when `--only` leaves the system's packages unread.
- Keys are unique across sources: a system package keeps its name, a flatpak its app ID, everything else is `<source>:<name>` (`cargo:ripgrep`), and a package inside a tool's virtualenv or `node_modules` is `<source>:<tool>/<name>` (`pipx:httpie/requests`, with `@<version>` added when one npm global holds two versions, or when two global folders hold the same package). `Package.label` is the name to show, read through `Package::label()`/`World::label()`; every screen and report shows labels and every `--json` `name` is the key. `whypkg why <name>` explains every package whose label is that name (every installer's copy), and falls back to the key when nothing has that label.
- `World.uses`/`used_by` link a package to the system packages it loads or runs on: each layer lists `needs` (the canonical path of a library a cargo binary's ELF `DT_NEEDED` names, placed through `ldconfig -p` in `backend/elf.rs` without running the binary as `ldd` would; each program a crate's manifest lists under `[package.metadata] runs`, found on `PATH`, since a program started at run time leaves no trace in the binary; the Python a virtualenv's `bin/python` points at; the node on `PATH`), and `read_world` asks `Backend::owners` once for all of them (`dpkg-query -S` with both `/usr`-merge spellings, `pacman -Qo`, `rpm -qf --qf '[%{FILENAMES}\t%{=NAME}\n]'`, where a plain `%{NAME}` inside the file iterator is refused). They are kept OUT of `deps`/`rdeps` on purpose: `bfs_root`, `rdep_count`, `pending`'s system-lib rule and "why is this here" must only follow edges an installer recorded, or a library apt pulled in for something else would read as "pulled in by" a cargo tool. They show as `uses`/`used by` in `why`, as `uses it`/`uses` rows in a dossier's lists (`World::needed_by_all`/`depends_on_all`) and the graph, and as the "but X still uses it" warning in `leaves`.
- Flatpak packages are keyed by application ID (`im.riot.Riot`) because that is what you type to remove one; the human name goes first in `description` ("Element - ..."), and the browser's `/` filter matches label + key + description + `details`, which is the only reason such packages are findable by their real name. The same mechanism makes apt's `code` findable by "visual studio" (its long description) and a cargo crate findable by its binary (`details` holds `binaries: rg`).
- `Package.origin` (`Repo`/`Local`/`Orphaned`) answers "did I sideload this?": apt combines the `[installed,local]` tag from `apt list --installed` with a scan of `/var/log/apt/history.log*` for `.deb` installs; pacman uses `pacman -Qm` (foreign); dnf uses `from_repo` (`@commandline` = local, `@System` = orphaned). The local-vs-orphaned split is best-effort since history logs rotate.
- The graph view (`src/tui/graph.rs`, `ctrl-g`) is a ratatui `Canvas` with braille markers, so it works in every terminal including tmux and over ssh - never reach for an image protocol (kitty/sixel) here, tmux breaks them. Nodes are spaced evenly *in y* (not by angle) so labels can never share a terminal row, on two alternating orbits so neighbouring labels start at different x; `POLE_FRAC` keeps the arc extremes off the centre line so trails do not run through each other. Labels sit on their planet's row and fan away from the middle. The layout tests encode all of this - if a change makes them fail, the visual bug is real.
- Rust ignores `SIGPIPE`, which made `whypkg pending --quick | head` panic; `restore_sigpipe()` in `main.rs` resets it to the default on unix. Never remove it, and keep report output going through plain `println!`.
- `capture()` forces `LC_ALL=C`, so labels, dates, and sizes parse regardless of the user's locale; never read tool output without it.
- A query whose failure would read as an empty answer (`unneeded()`, zypper's tables) goes through `capture_checked`, which turns a non-zero exit into an error quoting the tool's stderr; `capture` ignores the exit code because `pacman -Qm` and friends exit 1 for "none".
- `whypkg leaves` takes its unneeded group from `Backend::unneeded()`, the package manager's own autoremove answer (`apt-get -s autoremove`, `pacman -Qdtq`, `dnf repoquery --unneeded`, `zypper packages --unneeded`), never from the graph: the graph has no Suggests, virtual packages or alternatives, so it calls packages apt keeps "unneeded". Flatpak has no read-only way to ask, so its runtimes never appear there. It is queried only by `leaves`, so the browser's startup does not pay for it.
- `--json` output (`why`, `leaves`, `pending`) promises fixed field names and reason words in `--help`; renaming one is a breaking change.
- When resolving dnf/rpm deps: they are *capabilities*, not package names, mapped to packages via a PROVIDES+FILENAMES provider map (`src/backend/dnf.rs`). pacman gives `Required By` + `Install Reason` natively.
- Upgradables reflect the user's last sync (`pacman -Qu`, `apt list --upgradable`, `dnf repoquery --upgrades --cacheonly`), so like `apt list --upgradable` they are only as fresh as the last `apt update`; whypkg must not sync to refresh them.
- When touching the browser: it needs a real TTY on stdin and stdout, checked before the machine is read so a pipe fails at once. `--only` and `--upgradable` on the bare command conflict with every subcommand (`args_conflicts_with_subcommands`), so one typed before `why` is refused rather than ignored. `ctrl-[` is `esc` at the byte level and is handled explicitly as such.
- When touching keys: the browser is modeless, driven by views and footers. The screen is a boxed tab bar with ` whypkg ` on its border (`all`, then one tab per source that has packages, drawn with ratatui's `Tabs`), the body (the list in a box titled `<tab> (count)`, `(shown/total)` while filtered, with its scrollbar on the right border), a status line (the crumb on the left, replaced by a message while one shows; `show <word>` when not all and `row/total` on the right) and the footer, built by `widgets::key_footer` from the word constants there, with `? help` pinned at the right edge. Every tab keeps its own cursor and its own open dossier (`Tab.dossier`). Keys: `j/k ↑↓`, `ctrl-d/u`, `PageDown/Up`, `g G` move; `tab`/`shift-tab` step through the tabs; `↵` opens a package (a dossier pushes the one you were on onto `Dossier.back`, with its side and cursor) and `esc` walks back, then closes the dossier; `h/l ←→` focus needed by or depends on; `s` steps `Show` through all, manual, auto, upgradable (list only); `ctrl-g` opens the graph, and in the graph `h j k l` move, `↵` re-centres, `esc` unwinds the centres and then closes it, `ctrl-g` closes it onto the selected package's dossier; `r` re-reads in the background (`App::reload`, polled in the event loop, the screen stays usable, a second `r` while it runs does nothing, the footer leads with `⠹ reading 3/6`, a failure raises an alert once no other box is open, a landed read keeps the graph open on the same centre and every cursor on its package, and `rebuild_tabs` drops the filter through `drop_filter` first because cursors index the filtered rows); `o` opens the settings box (help panel only, since it works on every screen); `q` and `ctrl-c` quit from any view; `?` opens help. `/` filters the list in front of you (`App.filter`, every word of the query in the label, key, description or details, any case), never reordering it: while typed the footer row reads `/query█   N match   ↵ keep · esc back` and the query edits like a shell line (`line_edit.rs`), while kept the footer starts `/query · esc back`, and it is dropped by `drop_filter` whenever the view changes (tab, open, back, side, graph), which leaves the cursor on the package it was on. Cursors index the filtered rows (`App::focus_rows`), never the full list. Messages go green when something worked (`set_status`), yellow when not (`set_failed`), never red, and fade after `MESSAGE_TTL` (3 s).
- The settings box (`o`) edits `~/.config/whypkg/config.toml` (`src/config.rs`, `skip = [...]`, written with `toml_edit` so a person's comments and unknown keys survive): `↵` turns the source under the cursor on or off and `d` puts it back as it ships (read), each change written at once (a failed write puts it back and says why), and closing it with `esc` turns on or off, for this session, only the sources changed in it (so a run started with `--only` keeps the rest) and re-reads in the background, so a source turned off also leaves the dossiers and the graph; its key row is `↵ on/off · d default · esc close`. The help reader and alerts close with `esc` (`esc close`, `q` too, and `?` for help). Box pieces and key rows are in `src/tui/widgets.rs`; the help panel is the `HELP_ROWS` table in `render.rs`, one `(keys, what)` row per key under a lowercase heading, a row with no keys being a dim note, scrolling (`j/k`, `ctrl-d/u`, `g/G`) under a key row that never moves, with `vscrollbar` once it is taller than the box, so adding a row costs nothing but its line. Boxes stop above the status line, so what a settings change did stays in sight.
- Before the terminal is taken, `tui::while_loading` draws the braille WHYPKG wordmark decoding above a `reading apt, cargo [###---] 3/6` line on stderr, only after 150 ms and only on a terminal, from a timer rather than the readers' reports, and wipes it before the first frame.
- Testing other distros: build inside `archlinux`/`fedora`/`opensuse/tumbleweed`/`cachyos/cachyos` podman containers (`CARGO_TARGET_DIR=/tmp/...`) and regenerate fixtures from there.
- Keep one clap-derive subcommand per file with `Args` + `run()`, and heavy why-focused doc comments.
- The local dir is `apt-why`, but the crate, repo, and remote are all `whypkg`.

## Build / lint / test
- `cargo build --release`, binary at `target/release/whypkg`.
- Testing other distros means building inside `archlinux`/`fedora`/`opensuse/tumbleweed`/`cachyos/cachyos` podman containers (`CARGO_TARGET_DIR=/tmp/...`) and regenerating fixtures from there.
- When adding a layout or algorithm test, mutation-check it by reintroducing the bug and confirming the test actually fails, since a too-loose threshold silently passes.
- Backend parsers are checked against captured real output in `tests/fixtures/` via `include_str!`, `src/engine.rs` covers `bfs_root` including cycle safety, and `src/tui/graph.rs` covers graph layout, navigation and history invariants, with `World::from_edges()` (test-only, `src/model.rs`) building synthetic worlds. The cargo, pipx and uv parsing, the ELF reader, the apt and pacman owner parsers and the settings writer are tested inline in their files (the pipx/uv ones on a virtualenv built in a temp folder they delete); npm's folder walk, `ldconfig` lookups and the browser's keys have no tests.
- Run: `whypkg` (browse), `whypkg --upgradable`, `whypkg --only system,cargo`, `whypkg why <PKG>... [--json] [--only S]`, `whypkg pending [--quick|--kernel|--apps|--auto|--sizes|--json]`, `whypkg leaves [--quick|--json] [--only S]`. Point `XDG_CONFIG_HOME` at a scratch folder before trying the settings box (`o`), so the real settings file is never written.
- README screenshots live in `readme-assets/` (excluded from the crate) and are referenced by absolute GitLab raw URLs, because relative paths do not render reliably on crates.io; they must be pushed before publishing or the URLs 404. Because they are fetched live, replacing one needs no release: push the file and every rendered README updates.
- **Never capture a README asset by hand.** Every picture comes out of the `demo/` rig, which is the source of the assets the way a build script is the source of a binary: `demo/render.sh` renders every tape (or the ones named) in a container, so a machine needs podman or docker and nothing else: the image is `demo/Dockerfile`, vhs's own image pinned by digest with apt pointed at `snapshot.debian.org` at the date in its `SNAPSHOT` arg (nothing is installed on top yet), and each tape runs in a container of its own, as your user (`--userns=keep-id`, or docker's `--user`) so the images stay yours and the prompt ends in `$`, with no network, staging, recording from the repo root and tearing down with `demo/stage.sh down`. A UI change means rerunning a tape, never rearranging a terminal and cropping. Rendering deletes and rebuilds `demo/home/` (gitignored) and writes nowhere else, and `demo/` is excluded from the crate.
- The rig films an *invented* Debian workstation, never this machine: `demo/fixtures/` holds package data captured once from a throwaway `debian:sid` container plus a handful of hand-written packages (the sideloaded `code`, the orphaned `libssl1.1`, a kernel), and `cargo.tsv`, `python-tools.tsv` and `npm.tsv` for the other installers. `stage.sh` turns it into shim `apt`/`apt-mark`/`dpkg-query`/`flatpak` on `PATH`, a `/var/log` it can bind-mount, and the files cargo, pipx, uv and npm keep (`.cargo/.crates2.json` with each binary a copy of `true` grown with `truncate`, a virtualenv per tool whose `bin/python` points at the stage's `usr/bin/python3.14`, `bin/node` so node's prefix and so the globals are the stage's home), and `enter.sh` runs the release binary against that under `bwrap`. The `dpkg-query -S` shim places files by name (`libc.so.6`→libc6, `libgcc_s.so.1`→libgcc-s1, `python3.14`→python3.14-minimal, `node`→nodejs), so the `uses` links come out the same wherever the rendering machine keeps its libraries. Only `demo/capture.sh` needs podman and network, and only when the demo world should hold different packages. That indirection is also why the pictures render identically on a machine with no apt at all.
- Anything whypkg reads *directly* has to be masked in `enter.sh` or a real machine leaks into a frame: `/var/log` and `/var/log/apt` are bound to the stage, `/var/lib/flatpak` is a tmpfs because flatpak install dates come from a deploy directory's mtime and the system path is checked before the per-user one, and `/usr/local/lib/node_modules` is a tmpfs (when it exists) because npm's globals are read there whatever node's prefix is. Everything else the layers read is under `HOME`, which is the stage, and the environment is cleared, so `CARGO_HOME`, `PIPX_HOME`, `UV_TOOL_DIR`, `NPM_CONFIG_PREFIX` and `XDG_*` cannot point anywhere real. The flatpak leak reached a rendered frame once; check every new direct read. In render.sh's container bwrap cannot run unprivileged, so the container masks them itself: an empty tmpfs on `/var/log` (with podman's `notmpcopyup`, since the image is Debian and podman would otherwise copy its real apt history into it) that render.sh fills from the stage's logs, and empty tmpfs mounts on `/var/lib/flatpak` and `/usr/local/lib/node_modules`. `enter.sh` under `DEMO_MASKS=container` checks the three mounts, that the two folders are empty, and compares the logs with the stage's, refusing on any difference, and then opens the same shell under `env -i` instead of bwrap.
- Tape gotchas: VHS reads `Ctrl+G` as Ctrl+Shift+G, which the browser does not bind, so ctrl keys in a tape must be lowercase (`Ctrl+g`); the graph opens with the centre node selected and the centre is a column of one, so a tape must press Left/Right before Up/Down does anything; and VHS's parser rejects paths with digits in a directory name, so tape paths stay inside the repo. `shots.tape` makes `browse`, `search` (`/Element`, the filter while typed), `dossier` (`/libllvm`, `↵` twice), `graph` (`ctrl-g`) and `uses` (`/nodejs`, the npm globals that run on it); `report.tape` makes `pending`.
- Frame size is 1180x620 (112x28) for the browser and 720x520 for the report, because a browser row is 106 columns wide before its description and the report is 62: a wider frame is just dead space, and a forge scales an over-wide picture down until it is unreadable.

## Overview
Layout:
- `src/main.rs` - the clap `Cmd` enum and the dispatch match, nothing else.
- `src/commands/<verb>.rs`: one file per command, where `browse` reads the world and hands it to the interface, `why` prints a dossier, `pending` is the upgrade report, `leaves` lists what is worth a second look, `selfcmd` is `whypkg self`; `commands/mod.rs` picks the sources (`--only` or the settings file) and loads the world for a report.
- `src/tui/` is the browser: `mod.rs` owns `App`, the tabs, each tab's dossier and way back, the `/` filter, the background re-read and the terminal; `input.rs` every key; `line_edit.rs` the shell-line editing of the `/` query; `render.rs` the tab line, list, dossier, status line, footer, help and the settings box; `options.rs` the settings box's state; `boot.rs` the loading wordmark; `graph.rs` the braille dependency graph; `widgets.rs` the footer words and `key_footer`, the house box, key rows and scrollbar.
- Domain modules at the top level: `backend/` (one file per package manager, plus the layers and `elf.rs`), `load` (`Sources`, `Progress`, `read_world`), `config` (the settings file), `engine` (the distro-agnostic `bfs_root` trace), `model` (the `World`).


`whypkg` ("why is that package here? know it now") is a fast, cross-distro Rust CLI that investigates installed packages: did you install it or did something pull it in, when, alongside what, what needs it, and what it needs. It is a rewrite of the original bash `apt-why`/`apt-pending` scripts (kept in `legacy/`, excluded from the published crate). One distro-agnostic engine (`src/engine.rs`, with `bfs_root` as the "why is this here" origin trace) feeds an interactive ratatui browser (default, a tab per installer, with a `ctrl-g` braille dependency-graph view) and three reports: `why` prints a dossier, `pending` classifies upgradable packages by why they are present, and `leaves` lists what autoremove would take plus sideloaded and orphaned packages. Backends: apt, pacman, dnf, zypper, plus flatpak, cargo, pipx, uv and npm layered on top of any of them, with `uses` links from those to the system packages they load or run on. Crate and binary both `whypkg`, on crates.io, AGPL-3.0-only.
