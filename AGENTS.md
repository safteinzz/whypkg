# AGENTS.md

Working brief for an AI coding agent, not documentation for people (the README covers that): the rules, invariants and gotchas needed to change this project correctly without rediscovering them.

## Hard rules
- **whypkg never syncs or modifies the system.** It only reads package state; a write would betray the whole premise ("just tell me why this is here").

## Invariants and gotchas
- Adding a distro is one new `src/backend/<name>.rs` (implement the `Backend` trait) plus one line in `detect()`; nothing else changes. Parsing in each backend is pure functions, tested against captured real output in `tests/fixtures/` via `include_str!`.
- Flatpak is NOT a `detect()` backend: it *coexists* with the system package manager, so `src/backend/flatpak.rs` layers apps onto whatever `World` the system backend built (`augment()`), each tagged `Source::Flatpak`. `load_world()` in `src/commands/mod.rs` calls it whenever `flatpak` is on PATH, and falls back to `World::empty()` if flatpak is the only thing present.
- Flatpak packages are keyed by application ID (`im.riot.Riot`) because that is what you type to remove one; the human name goes first in `description` ("Element - ..."), and the browser's fuzzy search matches name + description + `details`, which is the only reason such packages are findable by their real name. The same mechanism makes apt's `code` findable by "visual studio" (its long description).
- `Package.origin` (`Repo`/`Local`/`Orphaned`) answers "did I sideload this?": apt combines the `[installed,local]` tag from `apt list --installed` with a scan of `/var/log/apt/history.log*` for `.deb` installs; pacman uses `pacman -Qm` (foreign); dnf uses `from_repo` (`@commandline` = local, `@System` = orphaned). The local-vs-orphaned split is best-effort since history logs rotate.
- The graph view (`src/tui/graph.rs`, `ctrl-g`) is a ratatui `Canvas` with braille markers, so it works in every terminal including tmux and over ssh - never reach for an image protocol (kitty/sixel) here, tmux breaks them. Nodes are spaced evenly *in y* (not by angle) so labels can never share a terminal row, on two alternating orbits so neighbouring labels start at different x; `POLE_FRAC` keeps the arc extremes off the centre line so trails do not run through each other. Labels sit on their planet's row and fan away from the middle. The layout tests encode all of this - if a change makes them fail, the visual bug is real.
- Rust ignores `SIGPIPE`, which made `whypkg pending --quick | head` panic; `restore_sigpipe()` in `main.rs` resets it to the default on unix. Never remove it, and keep report output going through plain `println!`.
- `capture()` forces `LC_ALL=C`, so labels, dates, and sizes parse regardless of the user's locale; never read tool output without it.
- When resolving dnf/rpm deps: they are *capabilities*, not package names, mapped to packages via a PROVIDES+FILENAMES provider map (`src/backend/dnf.rs`). pacman gives `Required By` + `Install Reason` natively.
- Upgradables reflect the user's last sync (`pacman -Qu`, `apt list --upgradable`, `dnf repoquery --upgrades --cacheonly`), so like `apt list --upgradable` they are only as fresh as the last `apt update`; whypkg must not sync to refresh them.
- When touching the browser: it needs a real TTY (errors cleanly otherwise). `ctrl-[` is `esc` at the byte level and is handled explicitly as such (`is_escape`).
- When touching keys: every screen takes the plain keys like the user's other TUIs: `j/k ↑↓` move, `q quit` (the whole app), `? help`, `esc back`. The list and a dossier filter through `/` (`App::typing`): the query edits like a shell line through `tui::line_edit`, `↵` keeps it, `esc` or ctrl-c drops it, and a kept query leads the footer as `/query · esc back`, so `esc` drops it before it leaves the dossier. `h/l ←→` flip a dossier between needed by and depends on. In the graph `esc back` unwinds the dig history, then closes it. `ctrl-g` keeps the one word `ctrl-g graph` on both screens because it turns the graph on and off. Footer words and box pieces are constants in `src/tui/widgets.rs`, footers are built by `key_footer`, and the help panel (`render::render_help`) is drawn one row short of the screen so the footer stays below it. It is the `HELP_ROWS` table in `render.rs`, one `(keys, what)` row per key under a lowercase heading, a row with no keys being a dim note, and a reader whose body scrolls (`j/k`, `ctrl-d/u`, `g/G`) under an `esc close` row that never moves, with `vscrollbar` on the right border once it is taller than the box, so adding a row costs nothing but its line.
- Footer entries are separated by ` · ` (`widgets::SEP`); the graph's colour legend is not, because its `●` bullets already separate the entries.
- Testing other distros: build inside `archlinux`/`fedora`/`cachyos/cachyos` podman containers (`CARGO_TARGET_DIR=/tmp/...`) and regenerate fixtures from there.
- Mirror the `sluuz` crate's conventions: one clap-derive subcommand per file with `Args` + `run()`, and heavy why-focused doc comments.
- The local dir is `apt-why`, but the crate, repo, and remote are all `whypkg`.

## Build / lint / test
- `cargo build --release`, binary at `target/release/whypkg`.
- Testing other distros means building inside `archlinux`/`fedora`/`cachyos/cachyos` podman containers (`CARGO_TARGET_DIR=/tmp/...`) and regenerating fixtures from there.
- When adding a layout or algorithm test, mutation-check it by reintroducing the bug and confirming the test actually fails, since a too-loose threshold silently passes.
- Backend parsers are checked against captured real output in `tests/fixtures/` via `include_str!`, `src/engine.rs` covers `bfs_root` including cycle safety, and `src/commands/graph.rs` covers graph layout, navigation and history invariants, with `World::from_edges()` (test-only, `src/model.rs`) building synthetic worlds.
- Run: `whypkg` (browse), `whypkg --upgradable`, `whypkg pending [--quick|--kernel|--apps|--auto|--sizes]`.
- README screenshots live in `readme-assets/` (excluded from the crate) and are referenced by absolute GitLab raw URLs, because relative paths do not render reliably on crates.io; they must be pushed before publishing or the URLs 404. Because they are fetched live, replacing one needs no release: push the file and every rendered README updates.
- **Never capture a README asset by hand.** Every picture comes out of the `demo/` rig, which is the source of the assets the way a build script is the source of a binary: `demo/render.sh` renders every tape (or the ones named) in a container, so a machine needs podman or docker and nothing else: the image is `demo/Dockerfile`, vhs's own image pinned by digest with apt pointed at `snapshot.debian.org` at the date in its `SNAPSHOT` arg (nothing is installed on top yet), and each tape runs in a container of its own, as your user (`--userns=keep-id`, or docker's `--user`) so the images stay yours and the prompt ends in `$`, with no network, staging, recording from the repo root and tearing down with `demo/stage.sh down`. A UI change means rerunning a tape, never rearranging a terminal and cropping. Rendering deletes and rebuilds `demo/home/` (gitignored) and writes nowhere else, and `demo/` is excluded from the crate.
- The rig films an *invented* Debian workstation, never this machine: `demo/fixtures/` holds package data captured once from a throwaway `debian:sid` container plus a handful of hand-written packages (the sideloaded `code`, the orphaned `libssl1.1`, a kernel), `stage.sh` turns it into shim `apt`/`apt-mark`/`dpkg-query`/`flatpak` on `PATH` plus a `/var/log` it can bind-mount, and `enter.sh` runs the release binary against that under `bwrap`. Only `demo/capture.sh` needs podman and network, and only when the demo world should hold different packages. That indirection is also why the pictures render identically on a machine with no apt at all.
- Anything whypkg reads *directly* has to be masked in `enter.sh` or a real machine leaks into a frame: `/var/log` and `/var/log/apt` are bound to the stage, and `/var/lib/flatpak` is a tmpfs because flatpak install dates come from a deploy directory's mtime and the system path is checked before the per-user one. That leak reached a rendered frame once; check every new direct read. In render.sh's container bwrap cannot run unprivileged, so the container masks both itself: an empty tmpfs on `/var/log` (with podman's `notmpcopyup`, since the image is Debian and podman would otherwise copy its real apt history into it) that render.sh fills from the stage's logs, and an empty tmpfs on `/var/lib/flatpak`. `enter.sh` under `DEMO_MASKS=container` checks both mounts and compares the logs with the stage's, refusing on any difference, and then opens the same shell under `env -i` instead of bwrap.
- Tape gotchas: VHS reads `Ctrl+G` as Ctrl+Shift+G, which the browser does not bind, so ctrl keys in a tape must be lowercase (`Ctrl+g`); the graph opens with the centre node selected and the centre is a column of one, so a tape must press Left/Right before Up/Down does anything; and VHS's parser rejects paths with digits in a directory name, so tape paths stay inside the repo.
- Frame size is 1180x620 (112x28) for the browser and 720x520 for the report, because a browser row is 107 columns wide and the report is 62: a wider frame is just dead space, and a forge scales an over-wide picture down until it is unreadable.

## Overview
Layout:
- `src/main.rs` - the clap `Cmd` enum and the dispatch match, nothing else.
- `src/commands/<verb>.rs` - one file per command: `browse` builds the world and hands it to the interface, `pending` is the report, `selfcmd` is `whypkg self`.
- `src/tui/` - the browser: `mod.rs` owns `App`, the frame stack and the terminal, `input.rs` is the event loop, `render.rs` draws the list, the dossier and the help panel, `filter.rs` the manual/auto filter and the fuzzy match, `graph.rs` the braille dependency graph, `widgets.rs` the shared key words, `key_footer` and the house box.
- Domain modules at the top level: `backend/` (one file per package manager), `engine` (the distro-agnostic `bfs_root` trace), `model` (the `World`).


`whypkg` ("wonder why the f* you have that package? know it now") is a fast, cross-distro Rust CLI that investigates installed packages: did you install it or did something pull it in, when, alongside what, what needs it, and what it needs. It is a rewrite of the original bash `apt-why`/`apt-pending` scripts (kept in `legacy/`, excluded from the published crate). Two modes share one distro-agnostic engine (`src/engine.rs`, with `bfs_root` as the "why is this here" origin trace): an interactive ratatui browser (default, with a `ctrl-g` braille dependency-graph view) and a `pending` report classifying upgradable packages by why they are present. Backends: apt, pacman, dnf, plus flatpak layered on top of any of them. Crate and binary both `whypkg`, on crates.io, AGPL-3.0-only.
